MILVUS · MULTIPLE INDEXES ON ONE FIELD

一列多索引
架构预研

Scalar 和 Vector 分开做。
Scalar 第一版可直接支持多个索引同时加载，并让查询自动选择一个能正确执行的索引；用户指定索引的入口也可同时保留。
Vector 第一版更适合“可建多个、本次 Load 每字段只选一个”，并支持查询含义和参数兼容时的在线替换。

已经确认：Load 选择是临时覆盖
只影响本次 Load；release 后回到该 collection 保存的默认索引。重启则恢复当前 Load 的选择。
Vector 真正同时加载多个，不是小预留
要把 QueryCoord、Segcore、查询计划和资源状态都改成按 indexID 工作，已经接近完整多 Vector 索引功能。
在线替换分两档
metric、打分含义和查询参数都兼容时，现有 Reopen 可做逐 segment 替换；否则无停机切换必须同时保留新旧索引。
本报告重点：说明每个能力要改哪些组件、会碰到哪些现有机制，不用“高 / 中 / 低”代替成本上下文。
这是架构预研，不进入具体类、字段、锁、writer、重试次数和调度细节。

先统一概念

默认索引、当前 Load 和单次查询不是同一层

长期保存
Collection 默认索引
用户不在 Load 中指定时使用。新 collection 的首个索引可初始化它；升级前已有 collection 则在功能启用后的第一次 Load 中安全初始化。
→
本次 Load
加载集合 + Load 默认索引
Scalar 可以是一组 indexID；Vector 第一版每字段最多一个。release 后这层消失，回到 collection 默认值。
→
单次查询
查询实际使用的索引
Scalar 可由 Milvus 按条件选择，也可由用户指定。Vector 若以后多加载，Search 必须最终落到一个明确 indexID。
重启：QueryCoord 恢复当前 Load 的选择，继续加载同一组索引；这不是回到 collection 默认值。
Release：删除当前 Load 状态；下次 Load 未指定时，再读取 collection 默认值。
已有 collection：第一次 Load 若本地默认不存在且字段只有一个候选，就保存该明确 indexID；若候选不唯一，要求用户或外部平台指定。不能在功能启用前写这个新状态。
已确认方向：Collection 默认值和当前 Load 选择都由各查询集群自己管理，不要求 Primary / Secondary 相同。
源码现状

“定义和构建”已经能区分多个索引；“加载和查询”仍按一个字段一个索引

定义 / 构建
DataCoord 已按 indexID 管理索引定义、构建结果和每个 segment 的索引文件。
→
Load 入口
Proxy 会把同字段索引压成一个 indexID；多个索引会互相覆盖，选择不稳定。
→
QueryCoord
已经保存 Load 选择，但检查和下发仍会遍历 collection 的全部索引。
→
QueryNode / Segcore
Go 层很多状态已按 indexID；普通 Scalar / Vector 运行时仍是 fieldID 对应一个索引。
已有在线替换基础
当前已有“修改并保存 Load 配置”和“Reopen segment 替换索引”两段能力，但它们尚未按用户选中的 indexID 连通。
选择还没有真正连通
QueryCoord 保存了选择，但没有据此精确过滤索引；因此现在不能可靠指定同字段的某个索引。
查询仍没有 indexID
Vector 查询计划主要携带字段和 metric；Scalar 表达式也直接取得该字段唯一索引。
含义：“Load 时只选一个并在线替换”不是从零开始；“同字段同时保留多个并按查询选择”则会碰到 Segcore 和查询链路的单索引前提。
报告中的成本判断均以这些当前行为为起点。
整体方向

定义、加载、查询三层分开；所有跨组件信息都使用明确 indexID

DataCoord / 元数据
保存每个索引定义与构建结果
一个字段可以有多个独立 indexID；每个 segment 的索引文件仍独立保存，不增加“索引组”。
→
QueryCoord
保存本次 Load 需要什么
按字段保存索引集合和 Load 默认索引；只检查并下发这次需要的 indexID；切换还要防止旧任务覆盖新选择。
→
QueryNode / Segcore
保存实际加载结果
Scalar 按 indexID 保留多个；Vector 第一版只保留一个，完整方案才按 indexID 保留多个。
→
Query
最后选中一个明确索引
用户指定时传 indexID；自动模式由查询执行层选择。Vector 选择必须与 metric 一起固定。
架构规则原因
不依赖索引列表顺序默认值、Load 选择和查询选择都保存明确 indexID，避免重启后行为变化。
期望状态与实际状态分开QueryCoord 保存“应该加载什么”，QueryNode 上报“每个 segment 实际有什么”，才能恢复未完成切换。
状态按 indexID，不只按 fieldID否则无法知道同字段两个索引中哪个缺失、哪个正在加载、哪个可以删除。
Scalar 与 Vector 开关分开两条查询路径和运行时改动不同，可以独立上线。
这是共同的大方向；Vector 是否真的多加载，决定 Segcore 是否也要完成多 indexID 改造。

推荐范围

把三个能力视为三个完整功能，不要求同一期一起实现

功能 S
Scalar 多索引
多个同时加载。Milvus 自动选一个能正确执行的索引；查询指定索引的通路同时保留。未来再提高“选得快不快”。
功能 V1
Vector 多定义、只加载一个
可建多个，本次 Load 每字段选一个。查询含义和参数兼容时，可利用现有 Reopen 做在线逐步替换。
功能 V2
Vector 多索引同时加载
多个同时驻留，查询先用固定的 Load 默认索引。Segcore、状态和资源都按 indexID 工作。
功能 V3
Vector 每次查询选择
用户指定或 Milvus 动态选择。查询计划、Growing、refine 和结果路径都要携带同一选择。
为什么可以分开说明
Scalar 候选可保持精确语义只有 JSON path、cast、文本分析方式和二次检查规则一致的索引才能放在同一候选集合；在此前提下，不同 segment 选不同索引或扫描仍可得到一致结果。
Vector 结果是近似的不同索引会改变召回、延迟和结果稳定性；不同 metric 的分数还不能直接合并。
运行时改造不同Scalar 多加载需要多索引选择；Vector V1 可以继续每字段只保存一个 Vector 索引对象，V2 才需要彻底改成按 indexID 保存多个。
推荐：先把功能 S 和 V1 分别作为完整能力设计；是否做 V2，由多 Vector 同时驻留的真实需求决定。
这不是临时半成品：V1 完整解决“先建新索引，再切换当前索引”；V2 是额外的多驻留能力，V3 是额外的每次查询选择能力。
边界澄清

多数“等不等、失败还是回退”可以后置；但状态必须先拆对

问题本轮必须决定的架构以后决定的用户语义
新 segment / Import / Compaction 是否等所有索引每个 indexID 的构建与加载状态独立；不能再用“字段有索引”或“collection 全部索引”混合判断。哪些索引阻塞数据可见、失败多久后放行。
指定索引只有部分 segment 可用QueryCoord 能知道具体缺失范围；查询计划能携带明确 indexID。立即失败、等待、扫描原始数据或回退默认索引。
Load 未指定 Scalar 索引Load 状态能保存一组 indexID 和一个默认项。默认加载全部、默认集合，还是只加载默认项。
默认 Vector 索引改成不同 metricmetric 与 indexID 绑定；切换必须保证一次查询内可合并。是否允许、是否要求显式确认、对客户端如何展示。
对你的判断：这些确实主要是产品语义，不应阻塞大架构；但当前 Milvus 的部分检查把它们绑定在“一字段一个索引”上，所以必须在架构层先拆成按 indexID 的事实状态。
本报告不替你决定：表格右侧全部标为实现阶段待定，不把某个默认行为偷偷写成架构约束。
后文只在某个语义会直接决定是否需要双加载、查询计划改造时，把它升级为架构决定。
SCALAR

目标：多个索引同时加载，自动选“能正确执行”的一个，并支持用户指定

要解决的问题
同一个 Scalar 字段可同时有 BITMAP、INVERTED、STL_SORT 等索引，查询怎样找到可用路径？
现状：表达式按 fieldID 取得唯一 Scalar 索引，再判断该索引是否适合本次操作；Milvus 没有比较同字段多个索引的公共路径。
用户指定
查询携带明确 indexID；但还要决定它绑定到整个字段，还是某一个过滤条件。具体缺失时失败还是回退，留作产品语义。
用户未指定
对每个过滤条件分别筛选候选并选一个；没有可用索引时，只有字段原始值仍可读才可以扫描。
第一版不承诺最快
现有统计不足，查询执行时机也有冲突。先保证选择稳定、结果正确，再单独建设更好的估算。
为什么适合第一版：只有查询语义完全相同的索引才互为候选；在此前提下，自动选择可以按过滤条件、按 segment 独立进行，不改变最终结果。
已确认“自动 + 指定”方向；指定索引的作用范围和原始字段值是否始终可读，仍是架构决定。
已确认 E · 按过滤条件

用户指定的 indexID 绑定到某一个过滤条件

你要决定的问题
同一查询里可以有多个字段，也可以在同一字段上有多个不同条件；一个 index_name 应该控制哪一部分？
例子：age > 20 AND age < 60 AND name LIKE "ab%"。整个查询只能指定一个 Scalar 索引明显不够，因此真正可选的是“按字段”或“按条件”。
方案 A：按字段指定
同一个字段上的所有条件都要求使用同一个 indexID。
  • API 和查询计划较简单。
  • 一个字段只有一个提示，容易解释。
  • 该索引可能支持范围条件，却不支持同字段的另一种条件。
  • 会限制同一字段在一条查询中使用多个索引。
方案 B：按过滤条件指定
每个过滤条件可以有自己的 indexID；没有指定的条件继续自动选择。
  • 表达能力完整，同一字段的不同条件可使用不同索引。
  • 与自动模式“每个条件选一个”保持一致。
  • API、表达式解析和查询计划需要能把提示绑定到条件。
  • 用户写法会比按字段更明确也更长。
已确定：方案 B。每个过滤条件可独立指定 indexID；没有指定的条件继续自动选择。查询级单个 indexID 不进入方案。
缺失时失败、回退或等待仍是后续产品语义，不影响这里的绑定范围。
已确认 F · 原始值可读

Scalar 多索引启用后，原始字段值始终有独立可读路径

现状：索引是否带原始值、字段数据是否保留以及 NGRAM 等索引的二次检查，很多判断仍以 fieldID 为单位。多索引后，同字段可能同时有能提供原始值和不能提供原始值的索引。
方案 A：保证字段原始值始终有可读路径
Scalar 多索引启用后，不依赖某个 indexID 提供原始值；扫描和二次检查始终有数据来源，但不要求全部常驻内存。
  • 没有候选时可以安全扫描。
  • NGRAM 等需要二次检查的路径清楚。
  • 索引增删不会意外拿走字段数据来源。
  • 可能增加 mmap、远端读取或字段数据的长期资源。
方案 B：按已加载索引能力决定是否保留
如果某个索引能提供原始值，就尽量不再保留字段数据。
  • 有机会节省部分资源。
  • 必须按 indexID 跟踪谁能提供什么数据。
  • 索引切换、删除和自动选择都要重新验证数据来源。
  • 扫描或二次检查可能在查询时发现数据不可用。
已确定：方案 A。不要求原始字段值全部常驻内存；减少 mmap、远端读取或字段数据资源可作为独立优化。
这是架构和数据保存问题，不是“缺索引时回不回退”的产品语义。
SCALAR · 成本上下文

成本主要在运行时多索引保存与表达式选择，不需要先建完整统计系统

部分当前行为需要承担的新职责与现有机制的冲突
Load 入口同字段只留下一个 indexID接受并传递本次 Load 的 Scalar indexID 集合不能再用 fieldID 到单值的表示
QueryCoord检查 collection 全部索引或字段是否有索引只检查本次 Load 集合；按 indexID 汇总每个 segment 的完成情况现有“字段级完成”无法区分同字段多个索引
QueryNode / SegcoreGo 层部分状态按 indexID，普通运行时一字段一个索引同字段按 indexID 保留多个 Scalar 索引，并可单独加载、删除、上报当前每字段只保存一个以及直接固定索引的路径要改
表达式执行直接取得唯一索引，再决定用索引还是扫描先列出候选，判断支持的操作，再选中一个并执行“能否正确执行”和“是否值得使用”目前混在一起
字段原始值是否可读会受字段数据和索引是否带 raw data 影响独立记录字段原始值是否可读，并记录每个 indexID 自己能否提供原始值不能再把某个索引的能力当成整个字段的能力
数据保存每个 indexID 已有独立文件继续复用，不需要新增组合文件主要增长是对象存储、Load 时间和 QueryNode 资源
工作边界：需要改多索引保存、Load 状态、选择流程和特殊 Scalar 路径；不需要为了第一版新增值分布统计、全局统计或复杂查询选择系统。
这比“只加载多个但永远用默认索引”多一层查询选择；最重的基础仍是 Segcore 从 fieldID 单索引改为 indexID 多索引。

具体固定顺序属于实现设计；架构只要求有稳定选择层和原始扫描候选。
已确认 G · 只留估算入口

第一版只预留可选估算入口；统计数据作为独立增强

现在就保留
支持哪些操作
每种索引回答本次条件是否能保证正确结果。这是第一版选择的基础。
小扩展点

小扩展点

允许考虑索引大小、需要遍历的词项、是否还要读原始数据；第一版可以全部返回“未知”。
目标还需要什么为什么不是简单增加一个分数
部分索引做局部优化把索引内部已有的命中数、词项数接到统一入口可逐种索引增加，不影响未知候选继续按固定规则选择
可靠选择更快路径每个 segment 的不同值数量、常见值、分布、字符串大小、索引冷热状态同一条件在不同 segment、内存状态和前置过滤结果下成本不同
比较索引与原始扫描把扫描也作为候选，并知道前面条件已经剩多少行只比较多个索引可能选中一个比扫描还慢的路径
已确定：第一版只预留“可用性 + 可选估算，允许未知”的接口形状，不提前保存完整统计。以后把更优选择作为独立增强。
这满足“以后可以估算”的架构边界，同时避免现在建设没有数据支撑的复杂系统。
SCALAR · 未来决策

什么时候选择索引，会直接影响估算是否准确和查询是否需要等待

当前机制：索引或原始数据通常在表达式正式执行前预取。普通 Scalar 索引往往先生成整个 segment 的结果 bitmap；原始扫描则能利用前面 AND 条件留下的 bitmap，只检查仍有效的行。
提前选择并预取
查询开始时按统计和规则选一个索引，提前准备数据。
  • 可以和其他工作并行，查询等待较少。
  • 不知道前置条件实际过滤结果。
  • 如果一百万行已经只剩十行，原始扫描可能更快。
执行到该条件时再选
看到实际剩余行数后，再比较索引与扫描。
  • 选择依据更准确。
  • 冷索引或远端数据准备会进入查询关键路径。
  • 需要调整当前预取安排。
可选折中：提前按规则准备一个索引；执行时如果剩余行很少，只在索引和原始扫描之间做第二次判断。
本轮不决定：第一版不承诺最快，因此不必现在改变预取架构；只需保证未来估算入口不被锁死在 Proxy 或 QueryCoord。
真正的选择应在 QueryNode / Segcore 执行侧完成，因为冷热状态和每个 segment 的数据分布都在本地。
同类产品

同类产品既有系统自动选择，也有用户控制路径；并非每个产品都原生同时支持

产品怎么用多个索引怎么选择对 Milvus 的启发
PostgreSQL同一列可有多个不同物理索引核心以自动选择为主；显式 hint 常依赖扩展每种索引应提供自己的估算，公共选择层再结合统计比较
MySQL同列多索引；支持可见 / 不可见索引自动选择，也原生支持 USE / FORCE / IGNORE INDEX自动与用户指定可以共存；但依赖采样、值分布以及内存 / 磁盘读取成本参数
ClickHouse多个 data skipping index 自动参与过滤可要求某个索引必须被查询使用，否则报错；不等于强制只使用它第一版按规则判断可用性且不承诺最快，是合理边界
Elasticsearch常通过有名字的 multi-field 表达不同索引方式查询显式选择字段路径这是多个命名字段，不是同一字段上可互换的多个物理索引
可直接借鉴
自动选择 + 用户指定并存；每种索引自己说明支持能力和可选估算。
不能直接照搬
Milvus 按 segment 执行，索引还可能 mmap、冷加载或位于远端，成本信息与传统数据库不同。
建议边界
先做正确规则；统计和更优选择按真实基准逐步增加，不在多索引第一版一次做完。
参考：PostgreSQL 索引成本估算与统计文档；MySQL 统计与索引提示文档；ClickHouse skipping index 文档。
调研结论支持 Scalar 第一版方案，但不支持在缺少统计时承诺“自动选到最快”。
VECTOR

先区分四种能力；它们不是同一个成本

V0
可定义、构建多个
对象存储保留多份索引文件，但 QueryNode 仍只加载一个。主要是解除元数据入口限制。
V1
Load 时选一个
每字段选明确 indexID；可改变已加载 collection 的选择。Segcore 仍可每字段只保存一个 Vector 索引对象。
V2
同时加载多个
同一个 segment 内保留多个；查询先固定使用本次 Load 的默认 indexID，不开放用户每次选择。
V3
Search 选择索引
用户指定或 Milvus 动态选择；查询计划、sealed、growing、refine 和结果合并都使用同一选择。
V0 → V1主要连通 Proxy、QueryCoord 与现有 Reopen，运行时仍是一个索引。
V1 → V2最重的一步：Segcore、Load 状态、增删、资源、原始向量路径都改为 indexID 多值；查询也要能明确取得固定的 Load 默认 indexID。
V2 → V3继续开放用户指定或动态选择，并修改 Growing、refine 和对外查询语义。
关键结论：只把 Load API 写成列表，但内部仍只支持一个，并不等于已经预留 V2；未来最重的运行时改造仍然存在。
后文分别说明 V1、V2、V3 的组件职责变化。
VECTOR · V1

Load 每字段选择一个：改动集中，现有 Segcore 单索引结构可以保留

部分当前行为需要改变什么可复用 / 冲突
Proxy / Load API不能稳定选择同字段具体索引接受 index_name，解析为稳定 indexID；未指定时读 collection 默认去掉遍历覆盖；不增加查询期选择
QueryCoord已保存 fieldID 到 indexID，但下发全部索引同时过滤每个 segment 的索引文件信息和 collection 级索引信息，只保留本次 Load 选择；再汇总切换进度否则查询计划仍可能读到另一个索引的 metric 或参数
QueryNode Go很多索引状态已按 indexID确保状态、资源和上报围绕被选中的 indexID改动相对集中
Segcore一字段一个 Vector 索引；Reopen 可替换继续每字段只保存一个，只接收当前选择的 indexID现有“先加载新索引、成功后发布”可复用
恢复QueryCoord 能恢复当前 Load 配置记录，但检查路径尚不使用该选择方案要求重启后按记录继续加载或切换；release 后回 collection 默认需要把恢复记录与 IndexChecker 真正连通
完整价值：用户可先构建 B，再把已加载 collection 从 A 改到 B；不需要删除 A，也不必先 release。
限制：同一时刻每个 segment 仍只有一个 Vector 索引；Search 不能在多个已加载索引间自由选择。
这是 Vector 第一版的推荐基础能力，且不是未来必须丢弃的临时实现。
VECTOR · V2

真正同时加载多个：Load 管理和 Segcore 都要从“字段单值”变为“indexID 集合”

部分需要承担的新职责受影响的现有机制为什么不能只改 API
Load 期望状态持久保存每字段 indexID 列表和 Load 默认项Load 配置比较、重启恢复、IndexChecker单值 map 无法表达 [A, B] 和只删除 A
QueryCoord按 indexID 增加、删除、检查；把期望状态与 QueryNode 上报的实际状态比较，动态得到完成进度当前字段级缺失判断和“全部索引”遍历否则同字段两个索引会混成一个状态
QueryNode Go加载、卸载、lazy load、资源核算和上报都保留每个 indexID少数明确拒绝同字段多个 Vector 索引的路径字段存在任意索引不再等于目标索引可用
Segcore 元信息indexID 找索引信息，同时保留字段到索引集合当前同字段后一个索引会被忽略metric、参数和能力必须属于具体 indexID
Sealed Segment按 indexID 保存多个 Vector 索引；独立增删、准备、warmup、统计资源LoadDiff、原始向量来源、refine、取消和回收都按 fieldID这是整个方案最大的运行时改造
固定查询默认即使不开放用户指定，查询也必须取得本次 Load 的默认 indexID当前查询只按 fieldID 隐式取得一个索引同字段有 A、B 后，不能再让容器顺序决定查询用谁
资源同时计算 A+B 的内存、本地磁盘、GPU / DiskANN 资源Reopen 当前资源检查较粗必须真实允许新旧或多个索引同时驻留
结论：完成这些变化后，产品即使默认只加载一个，也已经支付了“多个 Vector 索引同时驻留”的大部分成本。
V2 已需要内部固定默认 indexID；V3 的剩余成本是开放用户 / 动态选择并明确 Growing、refine 的查询语义。
已确认 A · A1 主方案

主方案只预留公共接口形状，Vector 本次 Load 每字段最多一个

你要决定的问题
是否愿意现在就改 Segcore，让 Vector 内部真正能同时保存多个索引？
现状：Scalar 多加载本来就需要“字段到 indexID 集合”的 Load 表示，因此公共 Load 模型做成列表成本不大；但 Vector Segcore 仍是一个字段一个索引。
方案 A：只预留公共接口
Load 数据形状支持列表，但 Vector 第一版校验每字段最多一个；内部继续只保留一个。
  • 能复用 Scalar 的公共模型，当前改动较小。
  • V1 是完整功能：可建多个、Load 选一个、在线换一个。
  • 未来做 V2 时仍需重做 Segcore 和查询链路。
  • 不能宣传为“运行时已预留多 Vector 加载”。
方案 B：预留真实运行能力
现在就完成 V2 底层，产品默认或文档仍推荐用户每字段只加载一个。
  • 以后开放用户每次查询选择，主要剩 V3 的入口和查询语义工作。
  • 可以支持严格在线切换和不同 metric 双加载。
  • 现在就承担 Segcore、资源、状态、恢复的大改。
  • 测试范围已经接近完整多 Vector 功能。
已确定：A1 为主方案。V1 是独立完整能力；A2 保留为单独预研支线，下一页给出可实现路径与真实成本。
A1 已确认；A2 的详细运行路径不进入主方案，但保留独立预研结论。
非主方案预研 · A2

A2 技术上可行，但成本接近完整 V2，不属于 A1 的低成本预留

边界：A2 让同字段多个 Vector 索引同时加载，但查询先使用固定 Load 默认；本页不包含用户每次 Search 选择或动态择优，它们属于 V3 和 C2。
1 · 状态模型
验证 [A] → [A,B] → [B]
Load 保存 indexID 集合和固定默认；QueryCoord 按 indexID 比较期望与实际状态，分别增加、删除和恢复。
2 · Sealed 主路径
一个 segment 同时保存 A、B
Segcore 按 indexID 保存、查询和删除；证明只删除 A 不影响 B。这是 A2 相比 A1 最大的改造。
3 · 严格切换
新查询用 B，旧查询继续 A
B 全部准备后改变本次 Load 的选择；等待网络、队列和执行中的 A 请求排空。Growing 按已确认 D1 处理。
4 · 资源与恢复
测最终占用与 Load 峰值
分别测 A+B 长期核算、临时内存、本地磁盘、GPU / DiskANN、多 segment 并行 Reopen 和重启恢复。
QueryNode / Segcore每个 indexID 独立加载、卸载、上报、核算资源，并管理 raw data / refine 能力。
查询即使没有用户指定，也必须在查询开始时固定 Load 默认 indexID，不能让各 segment 自己选择。
主要风险不是元数据，而是 Segcore 多索引状态、Growing 查询含义、旧请求排空和资源峰值。
预研结论：没有发现不可实现的架构障碍。若以后明确需要严格无停机切换或 Search 选择，应完整进入 A2，不能继续在 A1 上增加小补丁。
A1 仍是主方案；A2 作为额外能力独立评估和立项。
VECTOR · 在线替换

metric、打分含义和查询参数都兼容时，才可以逐 segment 在线切换

要解决的问题
Collection 已加载时，从索引 A 改为 B，能否不 release / reload？
现状：Reopen 已能在单个 segment 上先准备 B，成功后再替换 A；失败时 A 仍可查询。但同一请求只有一份 Search 参数，例如 IVF 的 nprobe 与 HNSW 的 ef 不能互换，因此同 metric 不是充分条件。
1
写入新 Load 选择与顺序
从 A 到 B 的顺序信息随 Reopen 传到 QueryNode，并在最终发布 segment 状态前检查，防止旧请求晚到。
→
2
逐 segment Reopen
只下发 B；单个 segment 保留 A，直到 B 加载成功并发布。
→
3
汇总完成进度
QueryNode 上报实际 indexID；QueryCoord 知道还有哪些 segment 在 A。
→
4
完成或继续重试
所有仍会接收查询的 segment 副本都到 B 后完成；中途重启按保存的目标继续。
资源峰值：B 已占资源时，A 因旧查询未结束还不能回收；每个正在切换的 segment 都会出现 A+B，多个 Reopen 并行会放大 collection 总峰值。
用户可见影响：过渡期不同 segment 分别用 A、B，召回和延迟会渐变；发布新状态时新查询还可能短暂重试，deadline 很短的请求仍可能失败。
允许渐进切换的前提：metric 与打分含义一致，同一份查询参数、refine 和 raw data 能力都能在 A、B 上正确工作。
待确认 B · 需要你的可用性要求

你真正要决定的是：切换期间一次 Search 能否同时遇到 A、B

为什么影响架构
允许混用可以复用现有逐 segment Reopen；要求每次 Search 统一使用 A 或 B，就必须先双加载。
硬边界：不同 metric 的分数不能直接合并；同 metric 但查询参数、打分含义或能力不兼容时，同一请求也不能同时访问 A、B。这里需要统一的是“每次查询选 A 还是 B”，不是所有机器同一瞬间替换内存。
方案 A：接受逐步切换
只对 metric、打分含义、查询参数和相关能力都兼容的 A、B 做渐进切换；其他情况 release / reload。
  • Segcore 继续只保留一个，复用 Reopen。
  • 改动集中，资源峰值只发生在正在切换的 segment。
  • 兼容索引过渡期的召回和延迟可能渐变。
  • 不兼容索引会有一次 unload / load 窗口。
方案 B：严格无停机切换
A 保持服务；B 在所有目标 segment 上准备好；新查询统一使用本次 Load 的 B，旧请求排空后再删 A。
  • 可用于严格一致切换，也可处理不同 metric。
  • 必须实现 V2，以及“查询开始时固定 indexID”的内部能力；不一定同时开放用户指定 API。
  • QueryCoord 要等待所有仍服务查询的副本准备 B，再改变本次 Load 的当前选择。
  • 携带 A 的请求可能还在网络或队列中，需要明确排空边界；不能只看 Segcore 当前引用。
  • Growing 也要同时服务携带 A、B 的查询，必须进入后文的 Growing 选择。
  • 切换期按 A+B 核算资源，并延迟回收 A。
当前建议：V1 只支持“查询含义和参数兼容”的渐进切换；其他组合第一版 release / reload。若都要求无停机，应进入 V2 和内部查询固定 indexID 的方案。
请确认：兼容索引的召回 / 延迟渐变是否可接受；不兼容索引是否允许 release / reload。
VECTOR · V2

从 [A] 改成 [A,B]，再改成 [B]，本质就是完整多加载状态管理

要解决的问题
Collection 不 release，能否在线增加或删除一个已加载 Vector 索引？
现状：Reopen 能替换一字段的单个索引，但删除和发布最终仍以 fieldID 为单位；无法安全表达“保留 B，只删除 A”。
Load 状态比较集合
从单值比较改为集合差异：需要新增哪些 indexID，需要删除哪些。
先增加 B
A 继续服务，B 在每个 segment 独立加载和上报；失败不能影响 A。
改变本次 Load 的当前选择
只有 B 达到要求后，才让新查询选择 B；不修改 collection 默认值。
最后删除 A
等携带 A 的请求从网络、队列和执行路径排空后，按 indexID 回收 A，不能误删同字段的 B。
无需 drop / reload 的成本不是增加一个 Alter API，而是完成 V2 的集合状态、Segcore 按 indexID 保存多个索引、资源核算、切换进度与查询选择。
与严格切换的关系一旦能安全完成 [A]→[A,B]→[B]，严格无停机切换的大部分底层能力已经具备。
因此，“在线 alter loaded index 集合”不能作为 V1 上的小补丁，应归入 V2。
已确认 C · A2 + V3 的查询规则

进入多加载查询阶段后，未指定使用固定 Load 默认，用户可显式指定已加载索引

A1 第一版边界：每字段只加载一个，真正的索引选择发生在 Load / Alter Load。Search 即使接受 index_name，也只能验证或指定当前唯一已加载索引，不能访问其他已构建但未加载的索引。
方案 A：固定 Load 默认 + 用户可指定
未指定时使用当前 Load 的默认 indexID；指定时使用该 indexID。
  • 行为稳定，易于解释和排查。
  • Search 计划只需携带最终 indexID。
  • 不会因负载或统计变化悄悄改变召回结果。
  • 不自动选择理论上更快的索引。
方案 B：每次查询自动选择
Milvus 根据 query 参数、索引能力和资源状态，从已加载集合中挑一个。
  • 用户可以少理解索引细节。
  • 仍需在查询开始时固定 indexID，不能让 segment 各自随意选择。
  • 需要定义召回、延迟、资源之间如何取舍。
  • 成本估算不可靠时，行为可能难以预测。
已确定：C1 是以后 A2 + V3 的主查询规则。它支持稳定默认和用户指定；C2 动态选择作为独立预研支线，不改变默认策略，也不扩大 A1 第一版范围。
用户指定的边界：架构能严格检查指定 indexID；索引缺失时失败、等待还是回退，是产品语义，不在本轮决定。
C1 已确认；下一页只解释 C2 为什么可行、又为什么不能顺带承诺“自动选最好”。
非主方案预研 · C2

C2 可复用 C1 的选择入口，但“自动选最好”需要新的统计和运行信息

边界：C2 只有在 A2 已同时加载多个索引、查询链能携带明确 indexID 后才有意义。用户显式指定时不进入动态选择；信息不足时回到 C1 的 Load 默认。
第一层 · 可行
筛出能正确执行的候选
排除 metric / 打分含义、查询参数、加载状态、refine、raw data 或 Growing 路径不满足的索引。
第二层 · 可渐进
按稳定规则选择
多个候选都可用时先用固定规则；无法判断返回 unknown，并使用 Load 默认。不需要一开始承诺最快。
第三层 · 独立大能力
估算最快或最好
ANN 索引不只速度不同，召回也不同；必须先定义延迟、召回和资源谁更重要。
需要的信息为什么需要
nq、topK、Search 参数、提前估算的过滤比例同一索引在不同查询形状下成本不同；查询开始前通常拿不到各 segment 的精确过滤结果。
segment 数量与大小决定整条查询需要完成多少工作。
mmap、缓存冷热、本地文件和硬件快照静态索引定义不能代表实际延迟；这些状态分散在 QueryNode，只能先使用有延迟的汇总信息。
索引类型、构建参数和离线基准用于估算延迟与召回取舍；线上通常无法直接知道真实召回率。
准确度边界：第一版估算只能使用查询开始前已有的统计或状态快照。若要先得到精确过滤结果和实时节点负载，再固定 indexID，需要“先收集、再选择、再执行”的两段查询流程，属于更大的独立改造。
可实现方向：能力检查 → 可选估算 → unknown 回到 Load 默认 → 查询开始时固定一个 indexID。所有 sealed segment 必须使用同一选择，不能各自动态挑选。
C1 是主方案；C2 的正确候选筛选可行，“自动选最快或最好”应作为独立查询增强。
VECTOR · V3 成本上下文

Search 指定索引不只是加一个参数；整条查询链都要携带同一 indexID

部分需要改变什么受影响的当前机制
Proxy / APISearch 可选 index_name；解析并确定最终 indexID；混合查询的每个子查询独立选择当前只有字段和 metric
查询计划携带明确 indexID 及它绑定的 metric；用户 metric 与索引定义不一致时能识别当前计划从字段唯一索引读取 metric
Sealed Segment按 indexID 找到 Vector 索引并执行，不能只按 fieldID当前 Vector 索引容器是一字段一个
Refine / 原始向量知道本次 Search 使用哪个 indexID、它是否支持 refine；原始向量可以来自字段数据或另一个能提供 raw data 的索引，但不能再按 fieldID 随便取当前 refine 和原始向量来源多按字段处理
Growing Segment说明用户指定的持久索引如何作用于 growing；选择的 metric、参数或算法无法由临时索引表达时，要有另一条执行路径当前每个 Vector 字段最多一个临时索引，不支持时直接搜索原始向量
结果合并一次查询的 sealed segment 必须使用同一明确 indexID；Growing 按单独确认的同查询含义路径执行不同 metric 或不同打分含义的分数不能直接混合
在 V2 之后的增量：最重的多索引驻留已经完成，但 V3 仍是一轮完整的查询链路修改和测试，不只是开放 API。
如果只做 V1，Search 指定未加载索引只有“不可用”这一种结果，产品价值有限。
已确认 D · 只严格约束 sealed

查询选择的 indexID 严格约束 sealed；Growing 使用兼容执行路径

现状：Growing Segment 每个字段最多只有一个临时 Vector 索引；未启用或不支持时搜索原始向量。查询为 sealed 选择的持久 indexID，只在 sealed segment 上有对应索引文件。
方案 A：查询 indexID 只严格约束 sealed
Growing 使用能保持同一查询含义的临时索引；无法表达时，在支持的 metric / 算法范围内搜索原始向量。
  • 不需要维护多份 Growing 索引。
  • 指定物理索引与 Growing 实际执行方式可能不同，但查询含义保持一致。
  • Growing 查询可能明显更慢；部分 sparse 算法或参数未必能用原始数据表达。
  • 必须长期保留可搜索的原始向量，可能阻止现有回收并增加资源。
方案 B：Growing 也严格对应每个 indexID
为每个需要的 indexID、metric 或算法维护自己的临时索引。
  • Sealed 与 Growing 的指定语义最一致。
  • 插入时要更新多份索引。
  • CPU、内存、写入延迟都会随份数增加。
  • Growing 的加载、回收和状态也要按 indexID 重做。
已确定：方案 A。Growing 使用兼容临时索引或原始向量；必须明确支持范围，不能承诺所有 Vector 或 sparse 算法都能保持相同查询含义。
只做 V1 或普通 V2 固定默认时可后置；一旦 V2 用于严格无停机切换，或开放 V3，每个查询都有 A/B 选择，都必须回答。
同类产品

成熟向量产品更常用“有名字的向量目标”，而不是自动选同字段物理索引

产品常见做法对本方案的启发
Qdrant / Weaviate一个对象可有多个有名字的向量；查询明确指定目标向量名字与 metric、索引配置绑定，用户选择稳定
Elasticsearch / OpenSearch用不同 vector field 或命名目标保存不同向量 / 配置没有发现成熟的“同字段多个物理 ANN 自动择优”语义
Vespa查询指定 tensor / nearest-neighbor 项查询目标明确，选择发生在计划开始前
pgvector同一列可为不同距离运算建索引；SQL 运算符决定 metric，PostgreSQL 再选物理索引metric 是查询语义的一部分；不同 metric 不能静默混用
支持用户指定是合理的
有名字的目标是成熟、易解释的做法，尤其适合不同 metric 或不同资源特征。
固定默认也合理
未指定时使用 Load 默认，行为稳定；不需要一开始解决 Vector 成本估算。
动态 auto 需谨慎
ANN 索引不仅快慢不同，召回也不同。自动改变索引可能让结果变化，不能只用“能正确执行”描述。
同类产品调研更支持“默认 + 显式指定”，不支持第一版承诺动态选择最佳 Vector 索引。
资源影响

对象存储、构建资源和 QueryNode 驻留资源要分开看

资源多定义、只加载一个多个同时加载
对象存储每个 segment、每个 indexID 都有独立文件；总体通常接近各索引文件之和相同，不因是否加载而改变
构建 CPU / 内存 / 时间每个索引都要独立构建；构建并发和排队受影响相同，主要由定义数量决定
QueryNode 内存按当前索引核算；在线切换时每个正在 Reopen 的 segment 需要同时容纳 A、B必须按 A+B+…核算和预留；实际内存页受 mmap、lazy load 和缓存淘汰影响
QueryNode 本地磁盘 / 缓存主要保留当前索引与切换临时数据DiskANN、mmap 和本地缓存的逻辑需求随索引数量扩大，实际占用受缓存策略影响
Load 时间与峰值只准备当前索引；多个 segment 并行 Reopen 会放大 collection 总峰值需要准备整个加载集合；加载临时内存可能让峰值高于最终 A+B
原始向量按当前索引能力决定是否额外保留通常不应每个索引复制一份，但必须明确哪个路径可提供 raw data / refine
为什么“推荐用户只加载一个”有价值：即使底层支持 V2，默认只加载一个仍能降低需要核算的内存、本地磁盘和 Load 工作量。
可复用与缺口：QueryNode 现有估算入口已经能累加多个索引信息；仍缺多索引运行状态、Reopen 的精确差量和 raw data 资源处理。
具体上限、资源配额和不同索引组合需要基准测试后决定，不写死在架构里。

已澄清 H · 固定规则

Secondary 收到 Drop Index 后正常执行，不重新否决 Primary 的权威 DDL

当前源码：Primary Drop API 只检查 Primary 本地状态；loaded collection 上 Vector Drop 会被拒绝。消息复制到 Secondary 后不会再次调用 Drop API，回调直接把 indexID 标记删除，因此 Secondary 没有否决权。
1 · 定义删除
Secondary 接受 Drop
索引定义是权威事实。重新做本地 loaded 检查并拒绝，会让 Primary、Secondary 元数据分叉。
→
2 · 本地引用收敛
清理默认值与 Load 选择
已删除 indexID 不能继续存在于 collection 默认或当前 Load 中；新查询不能再生成使用它的计划。
→
3 · 查询排空
旧查询结束后回收索引
已经开始的查询可以排空；随后 QueryNode 删除实际索引对象。旧 Reopen 任务不能把它重新加载回来。
→
4 · 恢复
重启不恢复已删除 indexID
QueryCoord 恢复时先与现存索引定义核对，旧 Load 状态不能把已删除索引带回来。
结论：你说得对，H 不应是架构二选一。外部平台可以提前切换 Secondary 来避免查询中断，但这只是可选运维动作，不是保证元数据正确的前提。
仍留到实现阶段：如果 Drop 的是当前唯一可用索引，本地进入不可查询状态还是自动切备用索引，属于产品语义。
固定不变量：任何默认值、Load 选择、查询计划和实际加载状态最终都不能引用已经删除的 indexID。

代码升级与功能启用分开；第一次写入新状态前都可以回滚

1
Secondary 先滚动升级

Primary 再滚动升级

启用前可回滚
外部平台确认需要的集群完成升级；如有问题，直接回滚代码版本。

分别打开功能
同一能力先在 Secondary 打开接受新状态的开关，再在 Primary 打开；之后才允许写入对应的新索引或 Load 状态。
本地保护：所有可能写入新状态的路径都检查本集群开关，包括普通 API、CDC 回调、恢复和导入元数据路径。
分开启用：Scalar 多加载与 Vector 多定义 / 只加载一个不必同时开放。
已有 collection：只在开关打开后的首次 Load 初始化本地默认；候选不唯一时必须显式指定。
回滚边界：第一次启用并写入新状态后，不再承诺回到不能识别这些状态的旧版本。
内核不主动查询其他集群版本；升级顺序、各集群开关和首次写入时机由 Cloud 或其他外部平台负责。
预研计划

用四条独立验证线回答可行性和资源成本，不进入详细实现

R1 · 共同基础
多定义与独立状态
验证同字段多个 indexID 能独立创建、构建、恢复、删除；梳理所有仍按 fieldID 合并状态的路径。
R2 · Scalar
多加载与正确选择
验证多索引驻留、轻量候选信息、按条件选择、用户指定范围和原始字段可读路径；不评价“是否最快”。
R3 · Vector V1
只加载一个时在线替换
连通 Load 选择、Reopen、防旧任务覆盖、进度和重启恢复；测兼容索引切换时的资源峰值与查询影响。
R4 · A2 / C2 非主方案
分别验证多加载与动态选择
A2 验证多驻留、固定默认和严格切换；C2 验证正确候选、可选估算、unknown 回到默认，以及不同查询形状和硬件下的稳定性。
需要输出的数据用来做什么决定
对象存储与构建时间增长确定每增加一个 Scalar / Vector 索引的长期存储和构建负担。
QueryNode 内存、本地磁盘、Load 时间判断 Scalar 多加载是否合理，以及 Vector V2 是否值得做。
兼容索引在线切换峰值与延迟确认 V1 的渐进切换能否满足线上要求。
重启、任务晚到、加载失败验证旧任务不能覆盖新选择，以及“新索引失败时旧索引继续可用”。
Import / Compaction 等等待语义只验证“架构可表达”，不在预研中固定默认行为。
